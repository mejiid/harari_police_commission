# Architecture Decision Records (ADR)

---

## ADR-001: Framework — Next.js
- **Decision**: Use Next.js as the primary framework
- **Reason**: Provides SSR/SSG out of the box (critical for SEO on a government site), unified frontend + API, strong ecosystem
- **Alternatives considered**: Plain React + Express, Nuxt.js, Astro
- **Tradeoffs**: Slightly more complex than a static site generator, but needed for CMS dynamic content

## ADR-002: Database — PostgreSQL
- **Decision**: Use PostgreSQL as the primary database
- **Reason**: Relational structure fits CMS content well, reliable, widely supported, good tooling
- **Alternatives considered**: MySQL, MongoDB, SQLite
- **Tradeoffs**: Requires a managed DB service in production (e.g., Supabase, Railway, or self-hosted)

## ADR-003: Authentication — Better Auth
- **Decision**: Use Better Auth for admin authentication
- **Reason**: Modern, framework-agnostic auth library with first-class TypeScript support, clean API, built-in session management, and Prisma adapter — fits this stack perfectly
- **Alternatives considered**: NextAuth.js v5, Clerk, Auth0, custom JWT
- **Tradeoffs**: Newer library (less community history than NextAuth), but actively maintained and better DX for this stack
- **Features used**: Email/password credentials, session management, role-based middleware

## ADR-004: CMS — Custom Admin Panel
- **Decision**: Build a custom admin panel rather than using a headless CMS (e.g., Strapi, Contentful)
- **Reason**: Full control, no third-party cost or vendor lock-in, simpler for this scope
- **Alternatives considered**: Strapi, Sanity, Contentful
- **Tradeoffs**: More development time upfront, but better long-term ownership

## ADR-005: Email — SMTP / Nodemailer
- **Decision**: Use Nodemailer with SMTP for contact form email delivery
- **Reason**: Simple, no external service dependency for basic email sending
- **Alternatives considered**: SendGrid, Resend, AWS SES
- **Tradeoffs**: SMTP credentials must be managed securely; transactional email services offer better deliverability at scale

## ADR-006: Internationalization — Translations Table Pattern
- **Decision**: Use a separate translations table per content type rather than adding language columns to the main table
- **Reason**: Cleaner schema, scales to more languages without schema changes, standard approach for multi-language CMS
- **Alternatives considered**: Column-per-language (title_en, title_am...), separate tables per language
- **Tradeoffs**: Slightly more complex queries (JOIN required), but far more maintainable long-term
- **Languages**: English (en), Amharic (am), Harari (har), Oromo (orm)

## ADR-007: i18n Routing — next-intl
- **Decision**: Use next-intl for frontend language routing and translation management
- **Reason**: Built for Next.js App Router, handles locale-based routing (/en/, /am/, etc.), good TypeScript support
- **Alternatives considered**: react-i18next, next-i18next, custom solution
- **Tradeoffs**: Adds a dependency, but saves significant i18n boilerplate

## ADR-008: Role-Based Access Control
- **Decision**: Two roles — `super_admin` and `editor`
- **Super Admin**: full access including publish, delete, user management
- **Editor**: create/edit drafts and upload files only, cannot publish or delete
- **Reason**: Separation of concerns — editors shouldn't accidentally publish or delete content
- **Implementation**: Middleware checks role on protected admin routes

## ADR-009: Hosting — Vercel + Neon + ImageKit
- **Decision**: Vercel (app), Neon (database), ImageKit (images), Vercel Blob (PDFs), Resend (email)
- **Reason**: 
  - Neon is serverless PostgreSQL — no idle costs, scales automatically, integrates natively with Vercel
  - ImageKit provides image CDN, optimization, and transformations out of the box — better than raw storage for public-facing images
  - Vercel Blob is the simplest solution for PDF storage when already on Vercel
  - Resend has excellent developer experience and reliable deliverability
- **Alternatives considered**: Supabase (DB + storage), AWS S3, Cloudinary
- **Tradeoffs**: Multiple services to manage, but each is best-in-class for its role

## ADR-010: SEO — Basic
- **Decision**: Basic SEO only — page titles, meta descriptions, Open Graph tags per page
- **Reason**: Government commission site doesn't require advanced SEO; Next.js Metadata API handles this cleanly
- **Includes**: sitemap.xml (auto-generated by Next.js), robots.txt, per-page meta tags
- **Out of scope**: Structured data (JSON-LD), advanced analytics, search console integration
